# Kite Tasks — project spec

A team task manager (spaces → projects → tasks) with List, Board and Calendar views, a task detail drawer, My Tasks home, Inbox, and a quick-create modal. Built for a team of 5–30 people. UI is bilingual: **Mongolian (default) and English**.

The visual source of truth is the `design/` folder (exported from Claude Design). These `.dc.html` files do not render standalone (they depend on a missing `support.js`), so **read them as source**: the inline styles give exact colors, sizes, spacing and states, and the `<script data-dc-script>` block at the bottom of each file holds the sample data, string tables (mn/en) and interaction logic. Match them closely. When a design and this spec disagree on a **visual** value (color, size, spacing, radius, shadow, typography), the design wins: use the design's value and update `apps/web/src/styles/tokens.css` / `palette.css`, `.claude/rules/design-tokens.md` and `docs/design-notes.md` to match. For anything non-visual (behavior, data model, stack, API), ask. `docs/design-notes.md` has per-screen notes, decisions, and the full palette extracted from the designs.

## Stack

- **Monorepo:** pnpm workspaces. `apps/web`, `apps/api`, `packages/shared`.
- **Frontend (`apps/web`):** Vite, React 18, TypeScript (strict), React Router, TanStack Query (server state), Zustand (UI state only), Tailwind CSS v4 driven by CSS variables (design tokens), dnd-kit (drag and drop), TipTap (rich text + @mentions), date-fns, i18next (mn/en), lucide-react icons, cmdk (⌘K palette), @floating-ui/react (popover/picker/tooltip positioning).
- **Backend (`apps/api`):** Node 22.12+, Fastify 5, TypeScript (strict), Drizzle ORM + drizzle-kit migrations, PostgreSQL 16, zod via `fastify-type-provider-zod`, argon2 password hashing, cookie sessions, `@fastify/websocket` for realtime, `@fastify/multipart` for uploads, `@fastify/helmet`, `@fastify/cors`, `@fastify/swagger` + `@fastify/swagger-ui` (OpenAPI 3.1 generated from the zod route schemas, Swagger UI at `/api/docs`, off in production unless `API_DOCS=true`), pino logging.
- **Shared (`packages/shared`):** zod schemas, DTO types, enums, event names — imported by both apps. Never duplicate a type across apps.
- **Dev infra:** `docker-compose.yml` with Postgres 16 (databases `kite`, `kite_test`, `kite_e2e`), plus an optional S3-compatible server (SeaweedFS, `--profile s3`). Attachments go through the `Storage` interface (`apps/api/src/storage/`): local disk under `UPLOADS_DIR` (default `apps/api/uploads`) or S3 (`STORAGE_DRIVER=s3`, `S3_*`), picked by `createStorage`.
- **Production:** `docker-compose.prod.yml` on one host (`docs/DEPLOY.md`): `apps/api/Dockerfile` (`node:22-slim`, multi-stage; migrations as a separate one-shot `migrate` service: `node dist/scripts/migrate.js`), `apps/web/Dockerfile` (Caddy serving the Vite build, automatic HTTPS for `DOMAIN`, proxying `/api` incl. the WebSocket so everything is same-origin; config `docker/caddy/Caddyfile`, which sets the SPA's CSP), Postgres 16, and a daily `pg_dump` + uploads tarball (`docker/backup/backup.sh`). Settings in `.env` from `.env.prod.example`. One API instance only (realtime, the login throttle and caches are in memory). First run: `node dist/scripts/init.js` (`pnpm db:init` in dev) creates the workspace and owner on an empty database; the demo seed refuses in production. No email delivery: creating an invite returns the link once and Settings → Members shows it to copy.
- **Testing:** Vitest everywhere; API integration tests with `app.inject()` against a real test database; Playwright for a few end-to-end flows (`apps/web/e2e/`, `pnpm e2e`: its own API on :3100 and Vite on :5273 over `kite_e2e`, reset and seeded in English by `pnpm --filter @kite/api db:e2e` before each run; signs in as Anu (owner) and Dorj (member)).

## Conventions

- TypeScript strict, no `any`. ESLint + Prettier. Small files, feature folders.
- API: REST, JSON, prefix `/api/v1`. Validate every input with zod schemas from `packages/shared`. Errors are `{ error: { code, message } }` with proper HTTP status.
- OpenAPI: every route's `schema` declares `tags` (one of the tags in `apps/api/src/docs.ts`), a `summary`, a `description` when behavior isn't obvious (role limits, 409 codes), and response schemas for success and error statuses. Public routes set `security: []`. Shared request/response schemas get `.meta({ id: 'Name' })` so they appear as named models. `test/docs.test.ts` fails if an operation lacks a tag or summary.
- Every query is scoped by the caller's workspace membership. Never trust IDs from the client without checking access.
- Auth: cookie `kite_session` (random 32-byte token; `sessions.id` stores its SHA-256; httpOnly, SameSite=Lax, Secure when `WEB_ORIGIN` is https), 30-day sliding expiry, capped at 90 days after sign-in. Login is throttled by failed attempts only (`apps/api/src/auth/login-throttle.ts`; 429 `RATE_LIMITED` + `Retry-After`); there is no per-IP request rate limit (an office behind one NAT must not be capped). Logs never carry cookies, invite tokens or query parameters (`apps/api/src/logging.ts`). Rich-text bodies accept only the editor's node/mark types and http(s)/mailto links. Uploads: 25 MB per file, `MAX_WORKSPACE_STORAGE_BYTES` per workspace. Protected routes use `preHandler: app.authenticate`, then `requireWorkspaceMember(request, workspaceId, minRole?)` or `loadProjectAccess(request, projectId, minRole?)` from `apps/api/src/auth/access.ts`. A resource in a workspace the caller isn't a member of answers **404** (never confirm it exists); 403 only for a member below the required role.
- CSRF: every POST/PUT/PATCH/DELETE must carry `Origin: WEB_ORIGIN` (rejected with 403 `CSRF_REJECTED` otherwise). API tests send it via `ORIGIN` from `test/fixtures.ts`.
- IDs are UUIDv7 (time-sortable). Timestamps are `timestamptz`. Due/start dates are `date` (no time).
- Ordering inside lists/columns uses fractional index strings (`fractional-indexing` package) in a `position` column (`text COLLATE "C"`, so keys sort byte-wise), so moving a card updates one row. Moves send the neighbors after the drop (`prevId`/`nextId`); the server places the item right after `prevId` (or right before `nextId`). Task positions are unique per status (`tasks_status_id_position_unique`), allocated under the project row lock and never reused (soft-deleted tasks keep theirs, so restore puts a task back in place).
- Every task mutation writes an `activity` row in the same transaction, then emits a realtime event after commit: use `mutateTasks` (`apps/api/src/tasks/mutation.ts`), which locks the project row, inserts the logged activity rows and emits on the `app.events` bus (`apps/api/src/events/bus.ts`) only after commit. Payload shapes: `activityPayloadSchemas` in `packages/shared`. Exceptions (event only, no activity row): a pure reorder (move within the same status, `task.moved`); subtask edits other than adding (`subtask.added`) and checking off (`subtask.completed`), i.e. rename, reassign, due, uncheck, reorder, delete (`subtask.changed`); comment edits and deletes; follow/unfollow (no event either). No-op edits write nothing.
- Frontend: every route is a lazy chunk (`route.lazy` in `apps/web/src/router.tsx`); the task detail view (TipTap) and the quick-create modal are lazy too and preloaded when the browser is idle. Only the guards and the shell are in the entry chunk.
- Frontend: all server data through TanStack Query hooks in `src/api/`. Mutations are optimistic for checkbox toggles, drag moves, and status/priority changes, with rollback on error. Destructive one-click actions never ask first: task delete, mark done and drag-into-Done show an Undo toast (`useDeleteWithUndo`, `useMoveUndoToast`); only comment and space deletes use `ConfirmDialog`. A deleted task's drawer/page is read-only (`TaskView.readOnly`, body `inert`) with a Restore banner. Error screens offer "Try again" (`ErrorState` refetches the errored queries; `ErrorBoundary` also resets when the browser comes online or the socket reconnects). UI state (`stores/ui.ts`) persists per account under `kite.ui.<userId>`. Typed `@Name` that was never picked from the popup is resolved into a mention on send (`components/editor/typedMentions.ts`).
- All UI strings through i18next (`mn.json`, `en.json`). Mongolian is the default. Take Mongolian copy from the `STR.mn` tables in the design files. Mongolian dates look like `10-р сарын 14`; English like `Oct 14`.
- Default timezone `Asia/Ulaanbaatar` (per-user override). "Today", "Tomorrow", "Overdue" are computed in the user's timezone.
- Accessibility: keep the aria-labels, focus-visible outlines (2px accent, 1px offset; accent-ink in dark) and keyboard support shown in the designs. `apps/web/e2e/a11y.spec.ts` runs axe (WCAG 2.1 A/AA) on every screen and overlay in light and dark; it must stay at zero violations. Text never uses `--text-faint` (2.6:1): de-emphasized text (out-of-month calendar days, done task titles) uses `--text-muted`; done calendar pills are struck through at full color (not 65% opacity). Non-task content inside `role="table"` sits in a row/cell (`FullRow` in `TaskTable.tsx`). Route tabs (`UnderlineTabs`) follow the ARIA tabs pattern: only the selected tab is tabbable, ←/→/Home/End move and open. A "Skip to content" link is the shell's first tab stop (`#main`). The task drawer traps focus (floating-ui `restoreFocus`) and on close returns it to the row/card/link that opened it (`data-task-key`), else to `#main`; closing replaces the history entry. Pickers open with the current value highlighted. `apps/web/e2e/drawer-focus.spec.ts` covers the skip link and the trap.
- Commit after each completed phase with a clear message.

## Data model (PostgreSQL)

- `workspace_members` — workspace_id, user_id, role (`owner`|`admin`|`member`), title (nullable job title, e.g. "Engineering lead": pickers, Workload, People), capacity_points (int, default 15: points this person can take on over the next 2 weeks, Workload capacity marker), joined_at. Admins edit title and capacity in Settings → Members.
- `workspace_holidays` — workspace_id, date, name (PK workspace_id + date). Public holidays skipped when counting working days (sprint days, burndown). Seeded with the 2026 Mongolian public holidays (`apps/api/src/db/holidays.ts`; migration 0006 adds them to existing workspaces); admin editing comes later.
- `spaces` — id, workspace_id, name, initial, color (palette key), position, created_by? (users, set null)
- `projects` — id, workspace_id (denormalized from the space, so `key` can be unique per workspace; composite FK `(space_id, workspace_id)` → spaces keeps it consistent), space_id, name, key (e.g. `APP`, unique per workspace), color (palette key), task_seq (int), position, lead_id? (users, set null: the default reviewer), created_by? (users, set null), archived_at, created_at. Every workspace member can see and edit every project. Archiving/restoring a project and deleting an empty space are for admins/owners and for the member who created it (`canManageCreated` in `packages/shared`; null `created_by`, i.e. rows from before migration 0007, means admins only).
- `project_members` — project_id, user_id (the project's team: header avatar stack, suggested assignees and @mentions; not an access boundary)
- `statuses` — id, project_id, name (nullable: null = default status, the UI shows the translated name for its category), category (`todo`|`in_progress`|`review`|`done`), color (nullable: null = the category's color), position. New projects get 4 defaults (name null): To Do / In Progress / In Review / Done.
- `sprints` — id, project_id, number (int, per-project sequence, unique with project_id → "Sprint 14"), name (nullable: null = "Sprint {number}" translated), start_date, end_date
- `tasks` — id, project_id, number (unique per project → shown as `APP-142`), status_id, sprint_id?, title, description (jsonb, TipTap doc), description_text (for search), priority (`urgent`|`high`|`medium`|`low`|`none`), size? (`S`|`M`|`L`|`XL`; points 1/3/5/8 via `SIZE_POINTS` in `packages/shared`), reviewer_id? (users, set null: entering a review status without a reviewer sets the person picked in the UI, else the project lead), start_date?, due_date?, position, created_by, completed_at?, created_at, updated_at, deleted_at?
- `task_assignees` — task_id, user_id
- `task_status_periods` — id, task_id, status_id (set null on delete), category (snapshot), entered_at, exited_at?, entered_by, exited_by? — exactly one open row (exited_at null) per task; written in the same transaction as every status change (create, status change, duplicate, project move, template apply), only through `apps/api/src/tasks/status.ts`
- `sprint_memberships` — id, task_id, sprint_id, added_at, removed_at?, added_by, removed_by? — one open row per task in a sprint; written wherever `tasks.sprint_id` changes, only through `apps/api/src/tasks/sprint.ts`. Committed = open at sprint start. Deferred constraint triggers (migration 0006) reject a commit where a task's status or sprint has no matching open period/membership; migration 0006 also backfilled both from the activity log (`kite_backfill_status_periods()`, `kite_backfill_sprint_memberships()`, idempotent)
- `activity` — id, workspace_id, project_id, task_id, actor_id, type, payload (jsonb), created_at. Types: `task.created` (with `status`, and `duplicateOf` for copies), `status.changed`, `size.changed`, `reviewer.changed`, `sprint.changed` (also logged on create-into-sprint and project move; snapshots `{id, name, number}`), `priority.changed`, `assignee.added/removed`, `due.changed`, `attachment.added`, `subtask.completed`, `comment.added`, `project.changed` (move to another project: new key there; the old key stops resolving), etc.
- `notifications` — id, user_id, type (`mention`|`assigned`|`comment`|`status`), task_id, actor_id, activity_id, read_at?, archived_at?, created_at
  Created by the notifier (`apps/api/src/notifications/`) from bus events: @mentions (comments, descriptions), new assignees, comments and status changes on followed tasks. Never for the actor or non-members. One per recipient per event: the highest type they have enabled in `notification_prefs` (mention > assigned > comment > status). An unread, unarchived one of the same type on the same task from the last 5 minutes is updated in place (latest actor/activity, `created_at` bumped). Snippets are read from the comment/description at query time. A daily in-process job archives notifications read more than 30 days ago.
- Plain tables (`users`, `sessions`, `workspaces`, `invites`, `favorites`, `tags`/`task_tags`, `subtasks`, `comments` with `parent_id` replies, `attachments`, `task_followers`: creator, assignees and commenters follow automatically) and every index: `apps/api/src/db/schema/`.
- Colors (`users.avatar_color`, `spaces.color`, `projects.color`, `tags.color`) are palette keys such as `violet`, `blue`, `neutral`. The frontend maps each key to exact light/dark values from the designs (`docs/design-notes.md` Appendix A).
- Online presence is ephemeral (kept in the WebSocket server's memory), not stored.
- Seed (`apps/api/src/db/seed/data.ts`) mirrors the designs; dates shift so Oct 8 2026 = today. Eight people: the seven in Main plus Bayarmaa T. (QA, `yellow`) from TaskDetail/Calendar. Job titles from the Reports designs (Product manager, Mobile engineer, Product designer, Frontend engineer, UX researcher, Data analyst, Engineering lead, QA); Anu is owner, Bat admin, the rest members; everyone's capacity is 15. App Redesign has Sprints 9–14 of 15 working days each, computed from today (Sprint 14 is current, today is its day 4; holidays skipped). `seed/history.ts` generates ~24 weeks of history (completed tasks, status periods, reviewers, sprint memberships with mid-sprint additions and carry-overs, comments with @mentions and replies, subtasks done by teammates) shaped to the Reports designs (weekly throughput, In Review the slowest stage, ~3 day cycle time, ~87% on time); generated history never touches Anu's tasks in the last two weeks (My Tasks) nor the shown Calendar month. Partner Portal has one completed task (Reports empty state "1 / 5"). `pnpm db:waits [KEY]` prints a project's median days per status. Where Calendar and My Tasks disagree about Anu's tasks, My Tasks wins (Calendar's past "AB" items are done, future ones reassigned).

## Routes (web)

- `/login`, `/invite/:token`
- `/` → redirect to `/my-tasks`
- `/my-tasks`, `/inbox`
- `/p/:projectId/list` · `/board` · `/calendar` (task drawer opens via `?task=APP-142`)
- `/s/:spaceId/list` · `/board` · `/calendar` (space-level views across all the space's projects; calendar has a project filter)
- `/t/:taskKey` (task as full page)

- `/reports` → `/reports/overview` · `/reports/sprints` · `/reports/workload` · `/reports/people` (admins/owner) · `/reports/me` (members: "My performance"). Period, scope, sprint, person and sort live in the URL.
- Global: ⌘K palette, `C` = new task modal, `G` then `I` = Inbox, `Esc` closes drawer/modal.
