# Kite Tasks — project spec

A team task manager (spaces → projects → tasks) with List, Board and Calendar views, a task detail drawer, My Tasks home, Inbox, and a quick-create modal. Built for a team of 5–30 people. UI is bilingual: **Mongolian (default) and English**.

The visual source of truth is the `design/` folder (exported from Claude Design). These `.dc.html` files do not render standalone (they depend on a missing `support.js`), so **read them as source**: the inline styles give exact colors, sizes, spacing and states, and the `<script data-dc-script>` block at the bottom of each file holds the sample data, string tables (mn/en) and interaction logic. Match them closely. When a design and this spec disagree on a **visual** value (color, size, spacing, radius, shadow, typography), the design wins: use the design's value and update `apps/web/src/styles/tokens.css` / `palette.css`, `.claude/rules/design-tokens.md` and `docs/design-notes.md` to match. For anything non-visual (behavior, data model, stack, API), ask. `docs/design-notes.md` has per-screen notes, decisions, and the full palette extracted from the designs.

## Stack

- **Monorepo:** pnpm workspaces. `apps/web`, `apps/api`, `packages/shared`.
- **Frontend (`apps/web`):** Vite, React 18, TypeScript (strict), React Router, TanStack Query (server state), Zustand (UI state only), Tailwind CSS v4 driven by CSS variables (design tokens), dnd-kit (drag and drop), TipTap (rich text + @mentions), date-fns, i18next (mn/en), lucide-react icons, cmdk (⌘K palette), @floating-ui/react (popover/picker/tooltip positioning).
- **Backend (`apps/api`):** Node 22.12+, Fastify 5, TypeScript (strict), Drizzle ORM + drizzle-kit migrations, PostgreSQL 16, zod via `fastify-type-provider-zod`, argon2 password hashing, cookie sessions, `@fastify/websocket` for realtime, `@fastify/multipart` for uploads, `@fastify/helmet`, `@fastify/cors`, `@fastify/swagger` + `@fastify/swagger-ui` (OpenAPI 3.1 generated from the zod route schemas, Swagger UI at `/api/docs`, off in production unless `API_DOCS=true`), pino logging.
- **Shared (`packages/shared`):** zod schemas, DTO types, enums, event names — imported by both apps. Never duplicate a type across apps.
- **Dev infra:** `docker-compose.yml` with Postgres 16 (databases `kite`, `kite_test`, `kite_e2e`), plus an optional S3-compatible server (SeaweedFS, `--profile s3`). Attachments go through the `Storage` interface (`apps/api/src/storage/`): local disk under `UPLOADS_DIR` (default `apps/api/uploads`) or S3 (`STORAGE_DRIVER=s3`, `S3_*`), picked by `createStorage`.
- **Production:** `docker-compose.prod.yml` on one host (`docs/DEPLOY.md`): `apps/api/Dockerfile` (`node:22-slim`, multi-stage; migrations as a separate one-shot `migrate` service: `node dist/scripts/migrate.js`), `apps/web/Dockerfile` (Caddy serving the Vite build, automatic HTTPS for `DOMAIN`, proxying `/api` incl. the WebSocket so everything is same-origin; config `docker/caddy/Caddyfile`, which sets the SPA's CSP), Postgres 16, and a daily `pg_dump` + uploads tarball (`docker/backup/backup.sh`). Settings in `.env` from `.env.prod.example`. One API instance only (realtime, the login throttle and caches are in memory). First run: `node dist/scripts/vade.js --email --name` (`pnpm db:vade` in dev) creates a **platform admin** (see Platform admin), who creates each workspace and its owner invite at `/admin`; the demo seed refuses in production. No email delivery: creating an invite returns the link once and Settings → Members shows it to copy.
- **Testing:** Vitest everywhere; API integration tests with `app.inject()` against a real test database; Playwright for a few end-to-end flows (`apps/web/e2e/`, `pnpm e2e`: its own API on :3100 and Vite on :5273 over `kite_e2e`, reset and seeded in English by `pnpm --filter @kite/api db:e2e` before each run; signs in as Anu (owner), Dorj (member) and Vade (platform admin)).

## Conventions

- TypeScript strict, no `any`. ESLint + Prettier. Small files, feature folders.
- API: REST, JSON, prefix `/api/v1`. Validate every input with zod schemas from `packages/shared`. Errors are `{ error: { code, message } }` with proper HTTP status.
- OpenAPI: every route's `schema` declares `tags` (one of the tags in `apps/api/src/docs.ts`), a `summary`, a `description` when behavior isn't obvious (role limits, 409 codes), and response schemas for success and error statuses. Public routes set `security: []`. Shared request/response schemas get `.meta({ id: 'Name' })` so they appear as named models. `test/docs.test.ts` fails if an operation lacks a tag or summary.
- Every query is scoped by the caller's workspace membership. Never trust IDs from the client without checking access.
- Auth: cookie `kite_session` (random 32-byte token; `sessions.id` stores its SHA-256; httpOnly, SameSite=Lax, Secure when `WEB_ORIGIN` is https), 30-day sliding expiry, capped at 90 days after sign-in. Native apps (`apps/mobile`) send `client: "mobile"` (+ optional `deviceName`) to `POST /auth/login` or `POST /invites/:token/accept` and get `session.token` in the body instead of a cookie (`authResultSchema`), then send `Authorization: Bearer <token>`: same `sessions` table, lifetime and login throttle, and a bearer request never gets a cookie set or cleared. A request with both is cookie auth (`readCredentials` in `apps/api/src/auth/plugin.ts`). The WebSocket takes the same header; a token is never read from the query string. Each session stores `client` (`web`|`mobile`), a `device_label` (the app's name, else parsed from the User-Agent), `last_seen_at` (moved with the daily sliding refresh) and a `public_id`: `GET /auth/sessions` lists my live sessions ("Signed-in devices", `current` flag), `DELETE /auth/sessions/:id` signs one out (someone else's → 404) and closes its sockets (4401), like `POST /auth/logout` does for the current one. Login is throttled by failed attempts only (`apps/api/src/auth/login-throttle.ts`; 429 `RATE_LIMITED` + `Retry-After`); there is no per-IP request rate limit (an office behind one NAT must not be capped), except on the public feedback form, which has no account to limit by (`apps/api/src/feedback/throttle.ts`: 5 submissions and 30 uploads per 10 minutes per IP). Logs never carry cookies, `Authorization` headers, invite tokens or query parameters (`apps/api/src/logging.ts`). Rich-text bodies accept only the editor's node/mark types and http(s)/mailto links. Uploads: 25 MB per file, `MAX_WORKSPACE_STORAGE_BYTES` per workspace. Protected routes use `preHandler: app.authenticate`, then `requireWorkspaceMember(request, workspaceId, minRole?)` or `loadProjectAccess(request, projectId, minRole?)` from `apps/api/src/auth/access.ts`. A resource in a workspace the caller isn't a member of answers **404** (never confirm it exists); 403 only for a member below the required role.
- CSRF (`originAllowed` in `apps/api/src/auth/plugin.ts`, also on the `/ws` upgrade): a POST/PUT/PATCH/DELETE carrying the session cookie must carry `Origin: WEB_ORIGIN` (403 `CSRF_REJECTED` otherwise, even with a bearer header too). Without the cookie, a bearer request needs no Origin, and a request with neither credential (the app signing in, the public form) passes only with no Origin at all: browsers always send one cross-site, so a foreign Origin is still 403. API tests send it via `ORIGIN` from `test/fixtures.ts`; `loginMobile` / `bearer` there sign in as the app.
- IDs are UUIDv7 (time-sortable). Timestamps are `timestamptz`. Due/start dates are `date` (no time).
- Ordering inside lists/columns uses fractional index strings (`fractional-indexing` package) in a `position` column (`text COLLATE "C"`, so keys sort byte-wise), so moving a card updates one row. Moves send the neighbors after the drop (`prevId`/`nextId`); the server places the item right after `prevId` (or right before `nextId`). Task positions are unique per status (`tasks_status_id_position_unique`), allocated under the project row lock and never reused (soft-deleted tasks keep theirs, so restore puts a task back in place).
- Every task mutation writes an `activity` row in the same transaction, then emits a realtime event after commit: use `mutateTasks` (`apps/api/src/tasks/mutation.ts`), which locks the project row, inserts the logged activity rows and emits on the `app.events` bus (`apps/api/src/events/bus.ts`) only after commit. Payload shapes: `activityPayloadSchemas` in `packages/shared`. Exceptions (event only, no activity row): a pure reorder (move within the same status, `task.moved`); subtask edits other than adding (`subtask.added`) and checking off (`subtask.completed`), i.e. rename, reassign, due, uncheck, reorder, delete (`subtask.changed`); comment edits and deletes; follow/unfollow (no event either). Workspace tag changes (create, rename, recolor, merge, delete) write no activity (history keeps its `{id,name,color}` snapshots) and broadcast `tags.changed` instead (`apps/api/src/routes/tags.ts`), which refetches tags and task lists/details. No-op edits write nothing.
- Frontend: every route is a lazy chunk (`route.lazy` in `apps/web/src/router.tsx`); the task detail view (TipTap) and the quick-create modal are lazy too and preloaded when the browser is idle. Only the guards and the shell are in the entry chunk.
- Frontend: List and Board load open tasks plus those completed in the last 14 days (`doneSince` via `useTaskQuery`, `features/views/useTaskQuery.ts`); `?done=all` loads every done task.
- Frontend: all server data through TanStack Query hooks in `src/api/`. Mutations are optimistic for checkbox toggles, drag moves, and status/priority changes, with rollback on error. Destructive one-click actions never ask first: task delete, mark done and drag-into-Done show an Undo toast (`useDeleteWithUndo`, `useMoveUndoToast`); only comment, space and tag deletes and tag merges use `ConfirmDialog` (they can't be undone). A deleted task's drawer/page is read-only (`TaskView.readOnly`, body `inert`) with a Restore banner. Error screens offer "Try again" (`ErrorState` refetches the errored queries; `ErrorBoundary` also resets when the browser comes online or the socket reconnects). UI state (`stores/ui.ts`) persists per account under `kite.ui.<userId>`. Typed `@Name` that was never picked from the popup is resolved into a mention on send (`components/editor/typedMentions.ts`). The project List has multi-select: `POST /projects/:id/tasks/batch` (per-task values, one transaction, through the same `applyTaskPatch` / `setTaskAssignees` as the single-task routes) plus `batch-delete` / `batch-restore`; one summary toast whose Undo sends the old values. Known `KEY-123` keys render as links in comments and are styled in the editor (⌘/Ctrl-click). Other people's realtime changes to status/assignees/due/priority show "X just now" for 10 s; a title changed while you edit it keeps your text and offers "Use theirs".
- All UI strings through i18next (`mn.json`, `en.json`). Mongolian is the default. Take Mongolian copy from the `STR.mn` tables in the design files. Mongolian dates look like `10-р сарын 14`; English like `Oct 14`.
- Default timezone `Asia/Ulaanbaatar` (per-user override). "Today", "Tomorrow", "Overdue" are computed in the user's timezone.
- Accessibility: keep the aria-labels, focus-visible outlines (2px accent, 1px offset; accent-ink in dark) and keyboard support shown in the designs. `apps/web/e2e/a11y.spec.ts` runs axe (WCAG 2.1 A/AA) on every screen and overlay in light and dark; it must stay at zero violations. Text never uses `--text-faint` (2.6:1): de-emphasized text (out-of-month calendar days, done task titles) uses `--text-muted`; done calendar pills are struck through at full color (not 65% opacity). Non-task content inside `role="table"` sits in a row/cell (`FullRow` in `TaskTable.tsx`). Route tabs (`UnderlineTabs`) follow the ARIA tabs pattern: only the selected tab is tabbable, ←/→/Home/End move and open. A "Skip to content" link is the shell's first tab stop (`#main`). The task drawer traps focus (floating-ui `restoreFocus`) and on close returns it to the row/card/link that opened it (`data-task-key`), else to `#main`; closing replaces the history entry. Pickers open with the current value highlighted. `apps/web/e2e/drawer-focus.spec.ts` covers the skip link and the trap.
- Commit after each completed phase with a clear message.

## Data model (PostgreSQL)

- `users.platform_role` — null for everyone except the platform admin (`vade`, migration 0020). See Platform admin.
- `workspace_members` — workspace_id, user_id (a person can be in several workspaces; each membership has its own role, title and capacity, while preferences, notification switches and out of office are per person), role (`owner`|`admin`|`member`), title (nullable job title, e.g. "Engineering lead": pickers, Workload, People), capacity_points (int, default 15: points this person can take on over the next 2 weeks, Workload capacity marker), joined_at, deactivated_at? / deactivated_by? (offboarding: no access, hidden from pickers/mentions/notifications/Workload, history kept; `activeMember` in `apps/api/src/auth/membership.ts` guards every access and picking query; `POST …/members/:userId/deactivate` hands open tasks, reviews and lead roles to one successor; re-inviting or `…/reactivate` brings them back). Admins edit title and capacity in Settings → Members. Out of office lives in `user_absences`.
- `user_absences` — id, user_id, start_date, end_date (both included), note?, created_by?. General out of office (replaced `workspace_members.away_until/away_note` in migration 0015, which copied current values): "Away until …" in pickers, @-suggestions, drawer chips, Workload and the standup strip, derived on the client with `currentAbsence` / `isAway` / `awayUntil` in `packages/shared` (back-to-back periods chain). Member and Workload DTOs carry `absences` (current + upcoming, `upcomingAbsences` in `apps/api/src/absences/query.ts`). Routes: `GET|POST /workspaces/:id/members/:userId/absences`, `PATCH|DELETE /workspaces/:id/absences/:absenceId`; the person edits their own (Settings → Profile), admins/owner anyone's (Settings → Members "Set out of office…"); overlaps answer 409 `ABSENCE_OVERLAP`. One person's time off is the same in every workspace they're in, so an admin of any of them may edit it, and a change drops the report cache and broadcasts `absences.changed` in each of those workspaces.
- `workspace_holidays` — workspace_id, date, name (PK workspace_id + date). Public holidays skipped when counting working days (sprint days, burndown). Seeded with the 2026 Mongolian public holidays (`apps/api/src/db/holidays.ts`; migration 0006 adds them to existing workspaces); admin editing comes later.
- `spaces` — id, workspace_id, name, initial, color (palette key), position, created_by? (users, set null)
- `projects` — id, workspace_id (denormalized from the space, so `key` can be unique per workspace; composite FK `(space_id, workspace_id)` → spaces keeps it consistent), space_id, name, key (e.g. `APP`, unique per workspace), color (palette key), task_seq (int), position, lead_id? (users, set null: the default reviewer), created_by? (users, set null), description? (TipTap JSON: the project brief under the header) + description_text, archived_at, created_at. Every workspace member can see and edit every project. Archiving/restoring a project and deleting an empty space are for admins/owners and for the member who created it (`canManageCreated` in `packages/shared`; null `created_by`, i.e. rows from before migration 0007, means admins only).
- `project_members` — project_id, user_id (the project's team: header avatar stack, suggested assignees and @mentions; not an access boundary)
- `statuses` — id, project_id, name (nullable: null = default status, the UI shows the translated name for its category), category (`todo`|`in_progress`|`review`|`on_hold`|`done`|`cancelled`, board order; `STATUS_CATEGORIES`), color (nullable: null = the category's color), position. Every project has 6 defaults (name null): To Do / In Progress / In Review / On Hold / Done / Cancelled; projects from before a category existed get it from `ensureDefaultStatuses` (`projects/statuses.ts`, run by `runMigrations` after the migrations). **On hold** is open but paused (still in My Tasks, Workload, overdue; not in standup Today chips, Where work waits or Aging). **Cancelled** is closed but not completed (`CLOSED_CATEGORIES` = done + cancelled, `isClosedCategory` in `packages/shared`): it leaves open lists, overdue and Workload, is trimmed after 14 days like Done, and never counts as completed in Reports or for feedback `notify_on_done`. API open-task filters use `openStatusSql()` (`tasks/status.ts`).
- `sprints` — id, workspace_id, number (int, per-workspace sequence, unique with workspace_id → "Sprint 14"), name (nullable: null = "Sprint {number}" translated), start_date, end_date (CHECK end ≥ start), created_by? (users, set null). **Shared by projects**: `sprint_projects` (sprint_id, project_id) lists the projects whose tasks can be in it (at least one, kept by the API). Migration 0018 turned each per-project sprint into a workspace sprint covering its project (workspaces where projects reused a number were renumbered by start date; history snapshots keep the old numbers). Routes (`routes/sprints.ts`): `GET|POST /workspaces/:id/sprints` (list with `projectIds` and live `taskCount`; any member creates), `PATCH|DELETE /sprints/:id` (admins/owner and the creator: `canManageSprint`); removing a project while its tasks are in the sprint → 409 `SPRINT_PROJECT_IN_USE`, deleting a sprint any task was ever in → 409 `SPRINT_IN_USE`; changes broadcast `sprints.changed` (no task activity). A task joins a sprint only from a covered project (`requireSprintIn`, 400 `INVALID_REFERENCE`) and keeps it when moved to a covered project. Settings → Sprints manages them.
- `tasks` — id, project_id, number (unique per project → shown as `APP-142`), status_id, sprint_id?, title, description (jsonb, TipTap doc), description_text (for search), priority (`urgent`|`high`|`medium`|`low`|`none`), size? (`S`|`M`|`L`|`XL`; points 1/3/5/8 via `SIZE_POINTS` in `packages/shared`), reviewer_id? (users, set null: entering a review status without a reviewer sets the person picked in the UI, else the project lead), start_date?, due_date?, position, created_by, completed_at? (entered done; kept between done statuses), closed_at? (entered done or cancelled; both set only through `closureStamps` in `tasks/status.ts`; migration 0021 copied `completed_at`), created_at, updated_at, deleted_at?
- `task_assignees` — task_id, user_id
- `task_status_periods` — id, task_id, status_id (set null on delete), category (snapshot), entered_at, exited_at?, entered_by, exited_by? — exactly one open row (exited_at null) per task; written in the same transaction as every status change (create, status change, duplicate, project move, template apply), only through `apps/api/src/tasks/status.ts`
- `sprint_memberships` — id, task_id, sprint_id, added_at, removed_at?, added_by, removed_by? — one open row per task in a sprint; written wherever `tasks.sprint_id` changes, only through `apps/api/src/tasks/sprint.ts`. Committed = open at sprint start. Deferred constraint triggers (migration 0006) reject a commit where a task's status or sprint has no matching open period/membership; migration 0006 also backfilled both from the activity log (`kite_backfill_status_periods()`, `kite_backfill_sprint_memberships()`, idempotent)
- `activity` — id, workspace_id, project_id, task_id, actor_id, type, payload (jsonb), created_at. Types: `task.created` (with `status`, and `duplicateOf` for copies), `status.changed`, `size.changed`, `reviewer.changed`, `sprint.changed` (also logged on create-into-sprint and project move; snapshots `{id, name, number}`), `priority.changed`, `assignee.added/removed`, `due.changed`, `attachment.added`, `subtask.completed`, `comment.added`, `project.changed` (move to another project: new key there; the old key stops resolving), etc.
- `notifications` — id, user_id, type (`mention`|`assigned`|`comment`|`status`|`standup_help`|`standup_reply`|`standup_resolved`|`standup_reminder`|`standup_digest`), task_id?, actor_id? (null for reminders/digests), activity_id, standup_group_id? / standup_date? / standup_entry_id? / standup_blocker_id? / standup_reply_id?, data? (the digest), read_at?, archived_at?, created_at. Each is about a task or a standup group (CHECK `notifications_subject_check`, migration 0016).
  Created by the notifier (`apps/api/src/notifications/`) from bus events: @mentions (comments, descriptions), new assignees, comments and status changes on followed tasks. Never for the actor or non-members. One per recipient per event: the highest type they have enabled in `notification_prefs` (mention > assigned > comment > status > standup types; every `standup_*` type follows the one `standups` switch, `prefKeyOf`). An unread, unarchived one of the same type on the same task (or standup update) from the last 5 minutes is updated in place (latest actor/activity, `created_at` bumped; `writeNotifications` in `notifications/deliver.ts`). Snippets are read from the comment/description (standups: the reply or the blocker) at query time. Standup notifications (`notifyStandup`, called after commit by the standup routes) go to the group's active members only and leave the Inbox when the person leaves the group. A daily in-process job archives notifications read more than 30 days ago. `project_notification_levels` (user_id, project_id, level `all`|`direct`|`none`; no row = all): `direct` keeps only mention/assigned, `none` drops everything for that project. Fixed rules:
- **Standup content is never used in Reports or in any performance metric.** That covers posts, items, blockers, replies, reactions, posting times, the late marker, meeting notes and meeting timing (per-person durations, totals: live mode only; `test/standup-meetings.test.ts` checks `src/reports/` never mentions standups). No report, export, Workload or People view reads the standup tables, and nothing aggregates a person's posts, late posts or blockers over time.
- Linking a task from a standup writes no task `activity`, no `task_references` row and doesn't touch `tasks.updated_at`.
- "Yesterday" is the group's previous standup day: the latest date before today (in the group's timezone) whose weekday is a group standup day and which isn't a `workspace_holidays` date.
- Out of office is `user_absences` (general, not standup-only).
